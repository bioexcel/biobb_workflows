# biobb_workflows — Technical Documentation

Monorepo containing the **BioExcel Building Blocks (BioBB) workflows** in six execution
"flavours": `python`, `airflow`, `cwl`, `docker`, `galaxy` and `jupyter`.

| Document | Content |
| --- | --- |
| [architecture.md](architecture.md) | Repo layout, per-workflow flavour matrix, the `common/` code-generation mechanism, jupyter submodules, how the flavours relate to each other |
| [ci.md](ci.md) | Every GitHub Actions workflow, the self-hosted runner infrastructure (`gh_runner`), secrets, Docker-in-Docker implications, known issues |
| [testing.md](testing.md) | Current state of the python tests, how to run them locally, static audit results, and the phased plan to test the other flavours |

## Quick facts

- **19 workflows**, each a top-level folder `biobb_wf_<name>/`.
- **6 flavours** are the possible sub-folders of a workflow; not every workflow has every
  flavour (see the matrix in [architecture.md](architecture.md)).
- **Single conceptual source of truth**: the ordered list of BioBB tool *steps*. The python
  flavour (`workflow.py` + `workflow.yml`) is the reference implementation used by CI. The
  CWL, Airflow and Galaxy flavours are derived artefacts that must be kept in sync manually
  (with generator scripts + manual fixes, see per-workflow `NOTES.md`).
- **Jupyter flavour** lives in *separate* repos (`bioexcel/biobb_wf_*`) mounted as git
  submodules at `<wf>/jupyter`.
- **Docker flavour** images are built from `common/docker/Dockerfile` (with per-workflow
  patches generated by CI) and published to **GHCR** as
  `ghcr.io/bioexcel/<workflow>:<version>` — one version label per workflow
  (see [ci.md](ci.md) §1.2).
- **CI**: test-what-you-changed, per flavour — a push to a workflow's `python/`, `cwl/`,
  `airflow/`, jupyter pointer or `docker/` paths runs that workflow's own tests for the
  touched flavour (python pytest / cwl / airflow / jupyter e2e; the docker e2e is the
  gate of the test-gated image publish — see [ci.md](ci.md) §1.2). The manual "Flavour
  e2e Tests" workflow covers ad-hoc subsets. Everything else in CI is code-generation
  (Dockerfile/README sync) or publishing. See [ci.md](ci.md).
- **Runners**: a self-hosted runner pool (Docker Swarm, `myoung34/github-runner`, labels
  `self-hosted,linux,mmbswarm`) on a remote server for light jobs; heavy python tests and
  image builds currently run on GitHub-hosted `ubuntu-latest`. See [ci.md](ci.md).
